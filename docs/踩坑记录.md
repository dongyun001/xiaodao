# 踩坑记录

> **用途**：记录本项目在开发、联调、入库、部署、运维中遇到的错误与坑点，供后续开发和运维快速定位，避免重复踩坑。
>
> **维护规则**：
> 1. **追加式记录，不删除历史**。修正旧条目时保留原文，另起“更新”说明；不要直接抹掉当时的结论。
> 2. **每条必须可复现**：写清现象、根因、修复、预防；尽量附“怎么验证”的命令或步骤。
> 3. **只记录事实，不指责个人**。写系统行为、配置差异、代码路径，不写“谁谁粗心”。
> 4. 日期用 `YYYY-MM-DD`；严重级别用 `P0 / P1 / P2`；状态只用 `已解决 / 观察中 / 待处理`。
> 5. 新条目复制下方模板；分类索引同步更新。无法确定的事项写“待确认/待定”，不要猜。

## 2026-10-22 DEEPSEEK_BASE_URL 必须带 /v1

- 场景/任务：配置 DeepSeek 的 OpenAI 兼容客户端。
- 现象/报错：请求 404/`Not Found`，日志里的实际 URL 是 `https://api.deepseek.com/chat/completions`，缺少 `/v1`；或 SDK 报路径不存在。
- 根因：OpenAI SDK 会在 `base_url` 后拼接 `chat/completions`。历史配置中一处写 `https://api.deepseek.com`，另一处写 `https://api.deepseek.com/v1`，两处不一致。
- 修复：统一配置为 `https://api.deepseek.com/v1`；启动时校验 `base_url.rstrip("/").endswith("/v1")`，不满足直接启动失败。

- 预防措施（可加入检查清单）：`.env.example`、README、`config.py` 默认值三处保持一致；配置单测覆盖不带 `/v1` 的输入。
- 相关文件/提交：`app/config.py`、`.env.example`。
- 严重级别：P1
- 状态：已解决

<a id="duration-pt60s"></a>
## 2026-10-22 ISO-8601 Duration PT60S 不能直接传给 Python 超时

- 场景/任务：历史环境配置使用 `DEEPSEEK_TIMEOUT=PT60S`、`INTENT_DEEPSEEK_TIMEOUT=PT10S`、`COMFORT_DEEPSEEK_TIMEOUT=PT20S`，需要转换为 Python 超时。
- 现象/报错：`TypeError: 'PT60S' is not a valid timeout`；`httpx.Timeout` 或 openai SDK 报类型错误；请求不受控。
- 根因：Java `Duration` 的 ISO-8601 写法，Python 的 `httpx`/`openai` 超时参数要秒数（int/float）。
- 修复：在 `Settings` 里用 validator 解析 `PT(\d+)S` 为正整数秒，同时接受纯数字；非法值启动失败。
  - 验证：`DEEPSEEK_TIMEOUT=PT60S python -c "from app.config import get_settings; print(get_settings().deepseek_timeout)"` 输出 `60`。
- 预防措施（可加入检查清单）：`.env.example` 用秒并注明兼容 `PTxxS`；单测覆盖 `PT60S`、`60`、`60.5`、非法值。
- 相关文件/提交：`app/config.py`、`.env.example`。
- 严重级别：P2
- 状态：已解决

> **更新（2026-10-22，步骤 10 收尾）**：`parse_duration` 已支持秒数与 `PTxxS` 两种写法。

<a id="pgvector-dimension"></a>
## 2026-10-22 pgvector 维度必须与 embedding 模型一致

- 场景/任务：更换 embedding 模型，或调整 `VECTOR_DIMENSION`。
- 现象/报错：`expected 1024 dimensions, not 768`、`different vector dimensions 1024 and 768`；或插入成功但检索报错。
- 根因：`knowledge_base.embedding` 是固定 `vector(N)`，HNSW 索引也按 N 建；模型输出维度不同，SQL 无法比较。

- 预防措施（可加入检查清单）：启动时查询列维度并与 Settings 比对；`.env.example` 固定 `VECTOR_DIMENSION=1024`；换模型前先出迁移方案。
- 相关文件/提交：`app/models/knowledge_base.py`、`alembic/`。
- 严重级别：P1
- 状态：已解决

<a id="vector-extension"></a>
## 2026-10-22 普通 PostgreSQL 镜像没有 vector 扩展

- 场景/任务：首次启动数据库或手工建库。

- 预防措施（可加入检查清单）：compose 使用 pgvector 镜像；init SQL 或 Alembic 第一步创建扩展；健康检查包含扩展查询。
- 相关文件/提交：`docker-compose.yml`、`alembic/versions/*`。
- 严重级别：P1
- 状态：已解决

> **更新（2026-10-22，步骤 10 收尾）**：初始迁移已包含 `CREATE EXTENSION IF NOT EXISTS vector;`。

<a id="alembic"></a>
## 2026-10-22 不要用 create_all/ddl-auto 代替 Alembic

- 场景/任务：建表、加字段、改索引。
- 现象/报错：启动自动改表、不同环境表结构漂移、无法回滚；生产出现缺列/索引。
- 根因：历史实现使用 `ddl-auto: update` 自动改表；Python 侧若用 `Base.metadata.create_all()` 也会绕过版本管理。
- 修复：以 Alembic 为唯一 schema 变更入口；首次迁移包含三张表和 `vector` 扩展；应用启动不自动改表。
  - 验证：空库执行 `alembic upgrade head`，再执行 `alembic downgrade -1` 和 `alembic upgrade head`，均成功。
- 预防措施（可加入检查清单）：CI 在空 PostgreSQL+pgvector 上跑迁移；迁移脚本评审；禁止生产 `create_all`。
- 相关文件/提交：`alembic/`、`app/database.py`。
- 严重级别：P1
- 状态：已解决

> **更新（2026-10-22，步骤 10 收尾）**：应用不调用 `create_all`；迁移由 Alembic 执行，容器启动时自动 `upgrade head`。

## 2026-10-22 LLM 超时/5xx 不能把异常抛给学生

- 场景/任务：主生成、意图归一化、共情回复。

<a id="multi-worker"></a>
## 2026-10-22 多 worker 会让 APScheduler 和内存状态失效

## 2026-10-22 步骤 9 要求 UPDATE alert_sent，但 AGENTS 禁止 UPDATE qa_log

- 场景/任务：实现危机告警，需要把发送结果回写到 `qa_log.alert_sent`。
- 冲突：`开发步骤提示词.md` 步骤 9 写的是"`qa_log.alert_sent` 只允许更新该字段，不开放通用更新接口"；而 `AGENTS.md` 与 `docs/接口契约.md` 规定 `qa_log` **只允许 INSERT 和只读查询**，禁止 ORM 写方法。按 AGENTS 的约定（冲突时以 AGENTS 为准），不能加 UPDATE。
- 处理：**先发告警、再写日志**。在 `answer_question` 里，`is_high_risk` 的结果先调 `_send_crisis_alert`，拿到结果后赋给 `alert_sent`，然后才 INSERT。这样不需要任何 UPDATE，语义仍是"只在发送成功后为 true"。
  - 代价：危机回复会等一次告警请求（超时 5 秒），失败不影响学生收到回复。这比"先回复、后台补写"更保守——后台补写必然要 UPDATE。
  - 验证：假钉钉服务（独立重算签名）下，危机 → `alert_sent=true` 且入库；同 openid 第二次 → 抑制、`alert_sent=false`；钉钉 `errcode=310000` → 学生仍收到回复、`alert_sent=false`；未配置 webhook → 回复正常、`alert_sent=false`。
- 预防措施（可加入检查清单）：需求里出现"回写某字段"时，先确认该表是否允许 UPDATE；不允许就把它改成"在写入前确定值"的流程。
- 相关文件/提交：`app/services/qa_service.py`、`app/services/alert_service.py`、`docs/接口契约.md` §4。

<a id="dingtalk-http-200-not-success"></a>
## 2026-10-22 钉钉 HTTP 200 不等于发送成功，必须看 errcode

- 场景/任务：判断告警是否真的发出去了。
- 现象/报错：钉钉在签名错误、限流、关键词不匹配等情况下仍返回 HTTP 200，响应体里是 `{"errcode": 310000, "errmsg": "sign not match"}` 之类。只看状态码会把失败记成成功，`alert_sent` 就会撒谎。
- 根因：钉钉自定义机器人的错误类型走业务错误码，不走 HTTP 状态码。
- 修复：`send_alert` 解析响应体，只有 `errcode == 0` 才算成功；其余记 `errcode` 与 `errmsg`（钉钉的 errmsg 不含我们的密钥，可以记录），webhook 与 secret 一律不进日志。
  - 验证：本地假服务返回 `errcode=310000` 时，`alert_sent=false` 且学生回复照常。
- 预防措施（可加入检查清单）：所有第三方 webhook/API 都不能只看 HTTP 状态码；先确认它有没有业务错误码字段。
- 相关文件/提交：`app/services/alert_service.py`。
- 严重级别：P2
- 状态：已解决
